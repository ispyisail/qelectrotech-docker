### A.1 What the code enforces

`LinkElementCommand::isLinkable()` (sources/undocommand/linkelementcommand.cpp) is the gate. For reports it checks **type and freedom only**:

```cpp
case Element::NextReport:
    if (element_b->linkType() != Element::PreviousReport) return false;  // type only
    if (element_a->isFree() && element_b->isFree()) return true;         // no order check
    ...
```

`ReportElement::linkToElement()` (sources/qetgraphicsitem/reportelement.cpp) re-checks the inverse type at link time and always unlinks first, so a report holds **at most one** partner:

```cpp
//ensure elmt is an inverse report of this element
if ((elmt->linkType() == m_inverse_report) && i) { unlinkAllElements(); connected_elements << elmt; ... }
```

The link picker (`LinkSingleElementWidget::setElement`, sources/ui/linksingleelementwidget.cpp) filters candidates to the **opposite** type:

```cpp
else if (elmt_type & ElementData::AllReport)
    m_filter = elmt_type == ElementData::NextReport
            ? ElementData::PreviousReport
            : ElementData::NextReport;
```

The label formula default is `%f-%l%c` (`ReportProperties::defaultProperties()`, sources/properties/reportproperties.cpp:31, setting `diagrameditor/defaultreportlabel`). `AssignVariables` resolves it — `%f` = `folioIndex()+1` (numeric folio, 1-based), `%l` = column letter, `%c` = column number — and `DynamicElementTextItem::updateReportText()` evaluates it against the **partner** element's diagram and position. So a report arrow prints *where the other end is*: `folio-column`, e.g. `5-B3`.

## Criterion 2 — placement, normalised by page size

Position is expressed as a fraction of the page (`cols` × `colsize` for width, `rows` × `rowsize` for height), so pages of different sizes are comparable. Because the arrow families ship in **two orientations**, the placement convention is axis-dependent: horizontal families (terminal on the west/east edge — `next_folio`, `previous_folio`, `going_arrow`, `coming_arrow`, and the plain Polish `nastepna_strona`/`poprzednia_strona`) place **next on the right, previous on the left**; vertical families (terminal on the north/south edge — the Polish `_1` variants and the SFC `jump_to`/`jump_from`) place **next at the bottom, previous at the top**.

### next

- **horizontal (x / page width)** (n=191): x fraction mean **0.717**, median 0.971, min 0.056, max 0.981 (IQR 0.324–0.972)
- **vertical (y / page height)** (n=21): y fraction mean **0.665**, median 0.844, min 0.172, max 0.875 (IQR 0.516–0.859)

### previous

- **vertical (y / page height)** (n=19): y fraction mean **0.277**, median 0.172, min 0.094, max 0.875 (IQR 0.156–0.203)

### Deviation counts

- next arrows on the left half (horizontal, x < 0.5): **61**
- previous arrows on the right half (horizontal, x > 0.5): **28**
- next arrows on the top half (vertical, y < 0.5): **5**
- previous arrows on the bottom half (vertical, y > 0.5): **3**

Conclusion: **“next lives on the right, previous on the left” holds for the majority, but the distribution is bimodal, not a single edge cluster.** For horizontal families the medians are cleanly separated — next median x ≈ 0.93–0.97, previous ≈ 0.07–0.10 — so normalising by page width does *not* overturn the brief's headline. But the brief's *mean* (760 vs 282) hid a second, systematic cluster: `industrial`'s `going_arrow` (next) falls in **two** groups — 59 at the right edge (x ≈ 0.95–1.0) and ~47 at an internal left position (x ≈ 0.25–0.35, with a few at 0.05–0.15) — and its `coming_arrow` (prev) splits into 84 at the left edge (x ≈ 0.05–0.10) and 17 at mid-page (x ≈ 0.5). In other words the industrial families use *two* placements, one at the correct edge and one at a fixed internal grid; only the latter is what a naive left/right rule would flag. Overall 61 next arrows sit on the left half and 28 previous on the right half. The convention generalises to vertical families as **next at the bottom, previous at the top** (medians 0.84 / 0.17). ## Where the brief was wrong or underspecified
